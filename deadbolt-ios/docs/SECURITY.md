# iOS security design

The app and AutoFill extension use the actual upstream Rust Deadbolt store and signed vault operations. Swift does not implement vault encryption or persist a decrypted credential cache. The shared App Group is `group.dev.zackbart.deadbolt`; absence of the provisioned container fails closed. The vault directory uses complete file protection and is excluded from device backups.

Device authentication enrolls a randomly generated upstream biometric wrapping key. The key is stored in the shared Keychain access group with `kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly` and `userPresence`. It never syncs through iCloud or migrates to another device. The operating system supports Face ID or Touch ID with device-passcode fallback. Locking or cancelling invalidates the active authentication context. Failed enrollment removes the unusable Keychain key and clears the wrapping slot when the session remains available. Removing the passcode deletes the protected Keychain item. The master password can still unlock the encrypted vault in the main app. Incorrect or missing shared-Keychain provisioning prevents enrollment and unlock.

The AutoFill extension never derives a password key with Argon2. The upstream default requires 64 MiB before other process allocations, which is unsuitable for a credential extension's constrained memory budget. People must unlock the main app and enable device authentication before AutoFill can independently open the same encrypted vault. The extension loads no networking stack during unlock.

Backgrounding clears published credentials immediately, invalidates pending Swift operations, cancels Rust networking, and queues closure of the encrypted database. Engine generations reject operations queued before locking. Completion generations prevent a late unlock, sync, or authentication result from restoring UI secrets after cancellation. The extension closes its database after completion or cancellation, locks on background, and expires a credential picker after 90 seconds. Cross-process database contention during handoff receives bounded retries; failures require closing Deadbolt and retrying, never creating an alternative secret cache.

Password suggestions contain website and account metadata in Apple's credential identity store. Passwords, TOTP secrets, wrapping keys, and passkey private keys are excluded from those identities. Automatic website matching uses exact normalized hosts; suffix matches are rejected. An authenticated person can explicitly choose another password and confirm a website mismatch. This override is unavailable for passkeys. Stale identity requests are resolved against current encrypted vault data before any password is returned.

Native passkeys use OS-provided registration and assertion requests. Apple verifies the caller's relying-party entitlement or web origin; the extension receives the relying party and client-data hash rather than the original web origin. The extension binds the encrypted record, RP ID, credential ID, user handle, allowed-credential list, and 32-byte challenge hash. Every ceremony requires a fresh protected-Keychain authentication before Rust receives `verified: true`. Upstream Rust creates ES256 credentials, attestation objects, authenticator data, and signatures, and persists passkeys through the encrypted vault's signed operations. Private keys never cross the Rust-to-Swift interface. Unsupported registration algorithms fail closed. The minimum deployment version is iOS 18, which exposes relying-party excluded credentials to the provider; these are forwarded to the Rust registration check.

Foreground sync runs after unlock and local mutations with debouncing, and the app can request it on becoming active. Networking runs as a bounded background Rust job while the authenticated foreground session remains open; CRUD does not wait behind peer timeouts. Sync status is polled while unlocked. Changes committed during a running sync coalesce into one following round. No background task reads protected keys or unlocks the vault. iOS does not promise continuous background execution; synchronization after locking requires the next foreground authenticated session.

CSV imports are parsed in memory, capped at 10 MB, and preserve passwords and OTP setup values without trimming secret data. Quoting errors, duplicate headers, and inconsistent rows fail before import. Apple Passwords, 1Password, and Bitwarden column aliases are accepted. Existing custom typed fields survive editing a login. Editing submits only changed supported fields with an atomic original-name and typed-field precondition; a remotely changed or deleted login is not silently overwritten or recreated. Import confirmation belongs to the app UI. The Rust import validates the planned batch before committing its signed operations atomically. Exact duplicates are skipped both against live items and within the same batch, so retrying the same file after an interrupted response does not duplicate committed entries. Import has an explicit destination vault.

Swift strings and framework credential objects are managed memory. Clearing references and closing the Rust store limits exposure, but Swift does not guarantee deterministic zeroization of all temporary plaintext copies. The Rust store owns its existing key-zeroization behavior. Plaintext credentials are not intentionally written to files or logs.

# Verification and remaining device checks

`CredentialDomainTests` covers exact-host matching and malicious suffix, userinfo, scheme, and backslash inputs. `SecretUtilityTests` covers RFC 6238 SHA-1 vectors, malformed OTP inputs, quoted CSV secrets and multiline values, malformed CSV, and representative export headers. The Rust bridge supplies its own real-store, biometric-unlock, and passkey cryptographic tests.

Unsigned simulator builds validate compilation and unit behavior. Real device signing must authorize the app group, shared Keychain group, and AutoFill provider entitlement for both targets. A signed physical-device check must verify enrollment, Face ID/passcode fallback, user cancellation, passcode removal, main-app/extension database handoff, system AutoFill activation, password fill, native WebAuthn registration and assertion, and background locking. Tests with simulated biometrics cannot establish hardware-backed Keychain enforcement. AutoFill and passkey runtime evidence must come from the operating system's actual credential-provider flow, not direct bridge requests alone.

All simulator sessions belong to the app integration agent; only one simulator is used at a time. No extra simulator is required for the shared-layer tests.
